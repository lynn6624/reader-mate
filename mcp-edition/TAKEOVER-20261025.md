## 为什么先修阅读进度

在独立临时目录对基线复现三项问题，未读取真实数据：

1. 写入损坏 JSON，调用 `load_progress()` 再 `save_progress()`，原文件被空库覆盖。
2. 两个快照先后更新不同成员，第二个快照保存会覆盖第一个成员的新进度。
3. 合成历史 ID `old.id` 和 `oldid` 同时存在时，`norm_who` 把两者合为一个，记录数从 2 变成 1。

这是交接稿阶段 0 “旧 progress 兼容、失败和重跑不丢数据”的未完成部分，比新增协作校对更早。没有改变现有正常阅读、身份管理或草稿功能的产品规则。

## 本次交付与边界

`load_progress` 严格读取并保留原始摘要，拒绝损坏/重复 JSON 键与非法容器；`book_progress` 保留历史 ID，区分同名于 offset/updated 的合法成员；`save_progress` 首次保存前私有备份、跨进程锁、快照比较、唯一临时文件及 fsync/原子替换。HTTP 的完整读改写使用同一锁。更新当前成员也保留其未知扩展字段。书籍删除在任何破坏性操作前先校验进度。

progress.json 是唯一进度正本。Markdown 镜像失败不会撤销已提交进度或返回保存失败；响应新增 `mirror_updated`，可在锁内从正本重建镜像。正文发布、多文件删除事务和任意硬件断电恢复不属于此修复的保证。运行方式和恢复边界见 [PROGRESS-PRESERVATION.md](PROGRESS-PRESERVATION.md)。

阶段 0 的上述代码缺口在本分支补齐；PR4 P0、管理员草稿保持现有实现。下一个功能阶段是 B 4.2 的五项 MCP 校对能力，之后才是审批页和可回滚发布。未在本次加入这些功能。
