# Reader-Mate｜MCP OAuth 授权接入需求单 v0.1

项目：小书桌（Reader-Mate）  
开发性质：独立功能分支 / 独立 PR  
优先级：P0  
实施原则：新旧接入并行、身份隔离不变、先验证后迁移、通用组件可复用

本文存档用户于 2026-11-02 提交的需求。阶段 0 审计见 [OAUTH-AUDIT.md](OAUTH-AUDIT.md)，实施及验收设计见 [OAUTH-PLAN.md](OAUTH-PLAN.md)。此文档不表示 OAuth 已实现或已部署。

## 一、背景

小书桌目前已有 MCP 服务及服务端读者身份体系。现有接入方式包括：

- 001：MCP URL + HTTP Header Key。
- 004：带私密 Key 的 MCP URL，由服务端验证身份。

两种方式目前均有实际使用场景，不应在新功能未经验证前移除。

项目希望新增符合 MCP 授权规范的 OAuth 接入能力，实现浏览器授权、服务端身份映射及独立凭证管理。目标不涉及模型 API、模型订阅授权或模型调用。

## 二、核心目标

用户在 ChatGPT 等兼容客户端中添加小书桌 MCP 时，可以：

1. 输入不包含任何私密凭证的 HTTPS MCP URL。
2. 自动触发 OAuth 授权流程。
3. 在浏览器中进入小书桌授权页面。
4. 使用邀请码或其他授权方式证明身份。
5. 确认本次授权所绑定的读者身份。
6. 由服务端向 MCP 客户端签发专用的 OAuth 凭证。
7. 完成连接，并按照授权身份访问已有 MCP 工具。

整个过程中，不向客户端展示或返回底层长期 MCP Key。

## 三、身份与凭证设计

### 3.1 身份与客户端解耦

既有读者身份（如 user、op001、op004）由服务端维护。OAuth 授权不创建新的独立阅读身份，而是将客户端授权映射至现有身份。阅读进度、批注、建议记录等数据继续归属于原有身份。

### 3.2 邀请码

邀请码仅用于证明授权资格，不直接充当长期访问凭证。推荐支持：

- 管理员生成邀请码。
- 邀请码绑定指定读者身份。
- 可设置过期时间。
- 可设置一次性使用。
- 使用后可查询授权记录。
- 可独立撤销客户端授权。

邀请码不得包含可以直接还原的底层 MCP Key。

### 3.3 OAuth Token

- OAuth Access Token 与原有长期 MCP Key 相互独立。
- Token 必须绑定具体的读者身份、目标 MCP 资源及授权范围。
- 支持有效期检查、撤销和必要的刷新机制。
- 服务端必须验证 Token，不得相信客户端自行声明的 viewer_id 或 who。
- 不得将 Token 转发给无关服务。
- Token 与邀请码均不得以明文写入日志或 Git 仓库。

## 四、技术要求

### 4.1 MCP OAuth 协议

按实施时有效的 MCP Authorization 规范实现，包括：

- Protected Resource Metadata；
- Authorization Server Metadata；
- Authorization Code + PKCE（S256）；
- 合规的客户端注册或客户端标识机制；
- OAuth state 和重定向 URI 校验；
- 授权码交换；
- Token 校验及生命周期管理；
- 对受保护 MCP 资源的权限检查。

优先采用经过维护的成熟 OAuth 组件，不自行发明认证协议。

### 4.2 HTTPS

新 OAuth MCP 入口使用正式 HTTPS 域名和有效证书。授权页面、回调及 Token 通信均应使用安全传输。不得仅因采用 OAuth 就认为原有的 HTTP 或 URL 凭证风险已解决。

### 4.3 与既有 MCP 业务层兼容

授权通过后，继续调用现有小书桌 MCP 工具及权限系统。不得绕过现有服务端身份判定。不得扩大 004 等读者原有的阅读、建议提交或查询权限。

### 4.4 安全边界

- 防止授权码重放、CSRF、Token 泄漏和重定向劫持。
- 严格验证 OAuth 客户端、目标资源和授权范围。
- 防止邀请码枚举与暴力尝试。
- 所有敏感配置使用安全配置或密钥管理机制。
- 对 OAuth 授权及撤销操作记录脱敏审计信息。
- 新旧接口并行期间，不允许通过旧接口绕过新接口的身份权限限制。

## 五、兼容与迁移要求

开发期间：

- 不修改 001 的 Header Key 接入行为。
- 不删除 004 的 URL Key 接入。
- 不影响既有小书桌管理端、读者端及 MCP 工具。
- OAuth 实验不得直接修改生产身份数据。

迁移期间：

1. 使用测试身份验证 OAuth 功能。
2. 通过 ChatGPT 等兼容客户端真实连接。
3. 确认 004 可以使用 OAuth 访问原有读书身份。
4. 验证阅读进度和建议记录连续性。
5. 验证撤销授权后无法继续访问。
6. 确认稳定后再迁移正式 004 连接。
7. 仅在旧 URL Key 入口不再被依赖后，撤销对应凭证。

001 的 Header Key 方式可以长期保留，不要求全部客户端强制改为 OAuth。

## 六、验收标准

| 测试项目 | 预期结果 |
| --- | --- |
| 无凭证访问 OAuth MCP | 返回规范要求的授权信息，不泄露受保护数据 |
| 添加 MCP URL | 兼容客户端能发现授权流程 |
| 浏览器授权 | 正确展示授权页面 |
| 有效邀请码 | 可完成身份绑定 |
| 无效或过期邀请码 | 拒绝授权 |
| OAuth 回调 | 成功交换凭证并完成连接 |
| MCP 工具发现 | 返回该身份允许使用的工具 |
| 004 身份访问 | 识别为 op004，不出现身份串号 |
| 跨身份读取 | 现有权限规则继续生效 |
| Token 过期或撤销 | 拒绝旧凭证，按规范重新授权 |
| 原有 Header Key | 保持兼容 |
| 原有 URL Key | 迁移完成前保持兼容 |
| 日志与审计 | 不泄漏完整凭证 |

审计注：上表保留原需求的 op004 表述；仓库旧网关实际绑定 `004`。实施必须绑定经核实的既有稳定 ID，不得为满足文字断言而重命名身份或改写历史数据，详见审计。

## 七、分阶段实施

### 阶段 0：只读审计

检查仓库现有 MCP 路由、身份门禁、代理配置及可复用组件。交付架构方案、安全风险与预计改动范围。不得直接修改生产配置。

### 阶段 1：独立 OAuth 接口

新增授权端点、身份映射和凭证管理，与现有接入方式并行。

### 阶段 2：端到端验证

优先使用测试身份和兼容 MCP 客户端，完成 OAuth 授权、工具发现、身份隔离与撤销测试。

### 阶段 3：ChatGPT 正式接入

将 004 的新 OAuth 授权绑定原有读者身份，确认数据连续、权限正确及断线恢复。

### 阶段 4：迁移与整理

撤销不再需要的 URL Key，关闭相应旧入口；输出脱敏技术文档、测试方案和可复用代码。

## 八、可移植设计

项目应尽可能拆分为：

**A. 通用 OAuth 层**：协议发现、授权流程、Token 生命周期、客户端兼容性、安全验证。

**B. 小书桌身份适配层**：邀请码、读者身份映射、工具权限、审计。

后续如 Leto 或其他 MCP 项目需要，可单独抽取通用实现。小书桌主要承担 OAuth 受保护资源及授权服务端角色，而 Leto 的目标是 OAuth 客户端接入，两者需分别适配，不能假设直接复制同一模块即可使用。

## 九、明确不做

- 不接入或调用任何模型 API。
- 不替换现有读书业务逻辑。
- 不重做小书桌全部登录系统。
- 不在第一阶段取消旧接口。
- 不要求加入 Leto 开发团队。
- 不实现与本次需求无关的账号注册、社交或复杂用户管理系统。

## 十、Codex 执行约束

先完成只读审计及技术方案，再进入实施。使用独立分支和 PR。必须提供自动化测试、端到端验证说明、回滚步骤和脱敏配置示例。未经明确确认，不修改生产部署或撤销任何现有有效凭证。

最终目标：让 MCP 客户端通过标准 OAuth 登录小书桌，获得与原有读者身份绑定的可撤销授权，而不是持有包含长期密钥的 URL。
